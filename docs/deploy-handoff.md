## 3. 已知会挡路的坑

### 3.1 🔴 `sudo` 需要密码 → rsync 必失败（**最先要解决的**）

`deploy-remote.sh` 用 `--rsync-path='sudo rsync'` 写目标目录。**这条 rsync 连接不分配伪终端**，
sudo 无法交互输入密码，因此**部署会在同步阶段直接失败**。

脚本对此有明确报错（搜 `deploy-remote.sh` 里的「rsync 同步失败」），不是静默失败。

三条出路，**任选一条**：

1. 给部署账号配置 **`NOPASSWD` 的 sudo**（最小范围：`rsync`，以及 `remote-install.sh` 需要的命令）；
2. 部署账号直接用 **root**；
3. 改部署形态（属于阶段 B 的范畴，不在本次范围）。

> 目标机当前的 `sudo` 需要密码，所以**开箱即跑不通**。这是第一个要拍的事。

### 3.2 原生依赖必须在 Linux 上构建

harness 的构建会跑 `build:native-system`，为**本机平台**编译 Node-API 插件。
产物 `native/system/packages/*/bin/` 已 gitignore。

**严禁把 macOS 的 `node_modules` 拷到服务器。**
服务器侧 `remote-install.sh` 会自己装、自己编译——这也是为什么目标机需要 `cc` / `make` / `node.h`。

### 3.3 部署前本地必须是干净的 pin 快照

`deploy-remote.sh` 现在有**三层保真检查**，任一层不过就在写入远端**之前**拒绝：

| 层 | 检查什么 |
| --- | --- |
| ① | 根仓工作树（tracked + **untracked**） |
| ② | 各 submodule 的 gitlink 是否偏离 pin（`+` / `-` / `U`），**递归** |
| ③ | 各 submodule 的**工作树内容**，**递归** |

**这意味着：本地有未提交改动时 `make deploy` 会被直接拒绝。先提交或还原。**

### 3.4 `log/` 等本地产物不会同步（已修，但要知道边界）

rsync 的排除清单（`deploy-remote.sh` 的 `RSYNC_ARGS`）已含 `log/`、`.env*`、`.claude/`、
`.netrc`、`*.log`。⚠️ **`.gitignore` 对 rsync 无效**——排除清单是手维护的黑名单，
新增任何会落地的本地目录时必须同步加进去，否则会进服务器。根治要等 allowlist 制品打包。

### 3.5 其他已知项

- 插件仓必须提交 `pnpm-lock.yaml`（服务器侧强制 `--frozen-lockfile`）。
- root 的 `sudo secure_path` 需包含 Node，否则会得到误导性的"未找到 node"。

## 4. 验收标准（阶段 A）

**每条都必须是可判定的**——"基本可用""看起来正常"不算通过。逐条给出**命令与输出**。

| # | 判据 | 怎么验 | 备注 |
| --- | --- | --- | --- |
| **A1** | `make deploy` 在**未改动的 `main`** 上退出码 0 | 记录退出码与完整日志 | 前置：§3.1 的 sudo 已解决 |
| **A2** | 服务处于运行态 | 服务器上 `systemctl is-active dsh` → `active` | |
| **A3** | 服务在服务器**本机**可达 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3080/` → `200` / `303` / `401` 之一 | DSH 只绑 `127.0.0.1`（有意），**不接受从外部直接访问** |
| **A4** | **重启存活** | `systemctl restart dsh` 后**重跑 A2 + A3** | 只验一次启动不算 |
| **A5** | **幂等** | 紧接着**再跑一次** `make deploy`，仍满足 A1–A3 | |
| **A6** | **回滚真的可用** | 注入一次可预期的失败（如部署期间在服务器上占用 3080，或把健康检查超时临时改短），确认脚本回滚且服务回到**上一版本**并仍满足 A2/A3 | ⚠️ 脚本注释明确：**"产物已回滚" ≠ "服务已恢复"**（重启是 `\|\| true`）。这条要如实记录你观察到的 |
| **A7** | **没有本地产物被同步上去** | 服务器 `$DEPLOY_DIR` 下 `find` 检查：**不存在** `log/`、`.env`、`.git`、`.claude/` | 抓 §3.4 那类泄漏 |
| **A8** | **原生依赖是 Linux 构建的** | 服务器上 `native/system/packages/linux-x64/bin/` 存在且非空 | 抓 §3.2 那类跨平台拷贝 |
| **A9** | **落地的源码 = pin 快照的内容**（不是工作树的） | 在服务器上对若干**源码文件**算 `sha256sum`，与本地同路径文件比对（排除构建产物与 `node_modules`） | 见下方说明 |

### 关于 A9：为什么不能只看部署标识

脚本会写 `${DEPLOY_DIR}/.dsh-deployed`（含 `sha=`），并在健康检查里比对它。
但**那个 SHA 是脚本自己写的**——所以它**必然一致**，**证明不了**"落地的字节就是该 commit 的内容"。
这是已知缺口（见 review P0-1），**当前没有完全可靠的验证手段**。

A9 因此落在一个**能真正抓到问题**的检查上：抽验源码文件的 sha256。
如果同步上去的是**工作树**而不是 pin 快照（有未提交改动、或某个 submodule 内容偏离），
这条就会不符。**只抽验源码，不碰 `node_modules` 与构建产物**——那些是服务器侧现场构建的，
本来就不该与本地一致。

### A6/A9 是"诚实项"

它们比其余各条更可能在首次执行时不过。**不通过也要如实记录**——
那正是阶段 B 要解决的问题，比一份"全绿"的假报告有价值得多。

## 5. 交付物

1. **一份执行记录**，每条验收标准对应：
   ```text
   已验证：<实际跑过的命令> → <结果/退出码/关键输出>
   未验证：<事项>（原因：<缺什么条件>）
   ```
   **禁止**把"按设计应该成立"写成"已验证"。
2. **失败现场**：出错点的**完整日志**（不是摘要）。`make deploy` 会 tee 到 `log/deploy-*.log`。
3. **手册修订建议**：凡是你发现 `deploy.md` 与实际不符的地方，逐条列出。
4. **一行结论**：阶段 A 是否跑通；若未通，卡在哪一条。

## 6. 明确不在范围内

- ❌ 改 `harness/` 或 `plugins/*` 的**内容**——它们是上游 pin，本仓不修改（需要适配时走 fork + 分支 pin）。
- ❌ 阶段 B 的目标态改造（非 root、`/var/lib/dsh`、`releases/<digest>`、hardening）。
- ❌ 生产启用。**A 跑通也不等于可上生产。**
- ❌ 把 `deploy/hosts` 或任何真实主机信息提交进仓库。
- ❌ 在共享机器上做破坏性试验（脚本对目标执行 `rsync --delete`，**误配不可逆**）。
