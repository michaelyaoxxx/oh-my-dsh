## 2. P0（会误导的表述）

### R-P0-1｜计数没有口径与命令，无法复核
- **位置**：§2 `警告` 区（“280 个 workspace package / 267 个含 lib/ 的包 / 293 个 .tsbuildinfo / Host 226 refs / Client 68 refs”）。
- **问题**：`280` 与实测 `278`（`find packages apps -name package.json -not -path '*/node_modules/*' | wc -l`）不一致，且未给测量命令与是否含 `vendor`。
- **处置**：修订轮在 §17 给出统一口径（278，packages+apps，不含 vendor/node_modules），并在 §2 警告区留“口径见 §17”指针。

### R-P0-2｜“10 个插件”与“10 个 bundle”混用
- **位置**：§17 结论（“10 个运行时插件” vs `log/link-plugins` 的“已挂载 10 个 bundle”）、§11。
- **问题**：`runtimeScope=required` 的组件=10；`link-plugins` 挂载的 bundle=10；两者恰好相等但**不是同一概念**（dsh-automation 等是 prebuilt，web-all 聚合 16 家族成员）。混用会在读者推导计数时出错。
- **处置**：修订轮统一为“10 个 runtime 组件 / 10 个 mounted bundle / 16 个家族成员跳过”。

### R-P0-3｜主证据与辅助日志的“基线关系”未显式声明
- **位置**：§1 基于清单（含 9/16 dev 日志）、§6.1（只写 setup 日志）。
- **问题**：正文大量结论只依据 9/15 setup 日志，却在 §1 列了 9/16 dev 日志，读者会误以为整篇基于两份日志。
- **处置**：修订轮在 §1 增加“主证据/辅助观测”两条显式边界。

### R-P0-4｜`lib/bin.js` 的“可执行权限由 tsdown 完成”缺少依据
- **位置**：§9.3 结论第 4 条。
- **问题**：日志只有 `Granting execute permission to lib/bin.js`，把话说到“由 tsdown 的 shebang/CLI 后处理完成”超出证据。
- **处置**：修订轮弱化为“由打包后处理完成（日志仅提示该动作，未定位到组件）”，并列入 §22 V5。

## 3. P1（可改进）

### R-P1-1｜数字应尽量给“来源列”
- **位置**：§17 关键数字表。
- **处置建议**：每行增“来源”（日志行 / 实测命令 / package.json）。已按需在修订轮补“实测”字样，完整来源列留 P2。

### R-P1-2｜tsconfig 是 JSONC，`node require` 解析失败应在正文首次出现处提示
- **位置**：§7.3/§8.2 提到 tsconfig；本评审实测 `require('./tsconfig.host.json')` 抛错（带注释 JSON）。
- **处置**：§24 术语已含 JSONC 条目；修订轮在 §17 数字注明“JSONC 容错解析实测”。

### R-P1-3｜dev 日志样本来源需注明
- **位置**：§10.4、§18.6、§20 引用 `log/dev-20260915T111700Z-sample.log`。
- **处置**：修订轮注明“该样本是手工拷贝自 9/15 实测 boot；同日原生 tee 文件为 `dev-20260915T132106Z-971922.log`”。

### R-P1-4｜运行期交互章节（§20-21）缺少 `[S]/[I]/[验]` 标注
- **问题**：§20/§21 大量是静态骨架，部分“认证 401/303”“token 轮换”等是本机实测（`[验]`），部分（waterfall 语义）是 `[S]`，未区分。
- **处置建议**：按仓库纪律给关键句标注（修订轮对高风险句加）。

### R-P1-5｜“入 index.html 注入 `__DSH_BOOT__`”需注明由 `client-modules` + `webserver/index-inject` 两端实施
- **位置**：§20.1。
- **处置**：已在本轮正文写明两端（服务端 `client-modules` 合成 + `webserver/index-inject`；浏览器 `boot.ts` 消费）。
